# Триаж Wazuh 5710: вход под несуществующим пользователем

**Дата:** 2026-10-19
**Стенд:** Wazuh 4.14.9 (manager + indexer + dashboard в Docker), агент 001 на Ubuntu 20.04 VPS
**Цель:** проверить, что цепочка «лог на сервере → агент → менеджер → алерт» работает, и разобрать событие по методике L1.

## 1. Алерт

| Поле | Значение |
|---|---|
| Правило | **5710** — `sshd: Attempt to login using a non-existent user` |
| Уровень | 5 |
| Группы | `syslog`, `sshd`, `authentication_failed`, `invalid_login` |
| MITRE | T1110.001 (Password Guessing), T1021.004 (SSH) |
| Тактики | Credential Access, Lateral Movement |

## 2. Событие

```
Oct 19 15:56:05 reckless-basis sshd[498795]: Invalid user baduser from 139.100.x.x port 3389
```

Разбор:

- `reckless-basis` — хост, с которого пришёл лог (агент 001)
- `sshd[498795]` — процесс и PID
- `Invalid user baduser` — sshd не нашёл такого пользователя
- `from 139.100.x.x` — источник подключения
- `port 3389` — порт на стороне клиента (не 3389 на сервере; это просто исходящий порт клиента)

Важно: пароль **не проверялся**. sshd отказывает до аутентификации, потому что учётной записи нет. То есть подобрать пароль к `baduser` невозможно — можно только гадать имена.

## 3. Атака или шум

Признаки, по которым L1 отличает одно от другого:

| Наблюдение | Вероятная причина |
|---|---|
| 1 событие, случайное имя | опечатка пользователя или единичный скан |
| 5–20 имён подряд за минуты | перебор имён (username enumeration) |
| Много `Failed password` для реального пользователя | подбор пароля |
| Разные IP, ровный интервал | распределённый брутфорс / ботнет |

В этом случае: одно событие, имя `baduser`, инициатор — я сам, для проверки пайплайна. Правило сработало корректно, инцидента нет.

## 4. Что проверять дальше

1. **Был ли успешный вход** с этого адреса после серии:

   ```bash
   grep "Accepted" /var/log/auth.log
   ```

2. **Сколько событий** 5710/5712 за период в одном источнике:

   ```json
   { "query": { "bool": { "must": [
       { "term": { "rule.id": "5710" } },
       { "range": { "@timestamp": { "gte": "now-1h" } } }
   ] } } }
   ```

3. **Есть ли другие правила** с тем же `data.srcip` (sudo, web, FIM) — один адрес в разных категориях поднимает приоритет.
4. **Не изменилось ли что-то на хосте** после события: новые процессы, файлы, сессии (`who`, `last`).

## 5. Действия

- Единичное событие без успешного входа → закрыть как шум, зафиксировать.
- Серия попыток → временная блокировка источника, проверка учётных записей, эскалация L2.
- Профилактика (уже сделано на этом сервере): `PasswordAuthentication no`, вход root только по ключу, `MaxAuthTries 4`.

## 6. Вывод

Алерт 5710 отработал по назначению: агент доставил запись `auth.log`, менеджер применил правило, событие попало в индексер. Успешных входов с указанного адреса нет — инцидента не зафиксировано. Событие использовано как проверка пайплайна.
